编译后看 `Debug\2024bizhang.hex` 的时间戳，**必须晚于所有源码**。

> 这个坑踩过很多次：跑半天发现跑的是旧固件，浪费大量时间。

AURIX Flasher 烧完，**按一下复位**（不然 CPU 可能停在 halt，程序不跑）。

### 4. 看日志

电脑上跑 `tools\run_log_save.bat`（或 `python car_log.py --out xxx.txt`）。
车和电脑要在同一个 WiFi 下（SSID/密码在 `zf_device_wifi_spi.h`）。

### 5. 看屏幕

- **S4** 切页面，也切灰度图/二值图
- **page1** = 图像 + 识别结果
  - 紫色线 = 参考线（`y=10/60`、`x=56/64`）
  - **红点 = 识别到的锥桶**
  - 红线 = 左边界，蓝线 = 右边界，绿/黄 = 补线后
- **page3** = 参数 + 状态，最后一行是 ToF 诊断 `To=读数 A=布防 H=命中数`

## 五、三个子系统的原理（改之前先看）

### 1. 循迹

从画面底部中心向左右各找**第一处白色跳变**，取这两条边线之间的区域当"一条道"。

两个关键设计：

**① 宽度归一化**：检测到的宽度会跳（一条道 ≈43px / 整条路 ≈116px），
所以按宽度分两种算法，并用迟滞（85/60）避免在 70 附近抖动。

**② 不可信帧保持**：`Point<=6`、`Point>=W-6`、`Result_Far_Row<40` 时（横道、过曝、丢线），
**沿用上一次的可信目标点**，不用垃圾数据打方向。

### 2. 锥桶（重点，改之前务必看）

**红色锥桶在灰度图里是白的。** 红色灰度 ≈76，二值阈值 ≈48，所以整体变白，和车道线一样。
区分只能靠**宽度**：车道线 2~3px，锥桶白箍 5~10px。

**最重要的约束：变道只能靠"时间"，不能靠"误差"。**

```c
pt = Point_Mid ± CONE_LANE_HALF;   // 绝对目标点
```

但检测到的车道是**跟着车走的**——车往左挪，车道在画面里也往左挪，`Point` 又回到 60，
误差重新出现，于是**一直往左打**。所以变道的量只能靠固定时长控制。

**完整流程：**

```
看到锥桶(CN>=2) → 用近端锥桶位置定方向 → 满舵打 1.0 秒 → done=1
                                            ↓
                            之后看得见锥桶也不再变道
                                            ↓
                            锥桶连续 1 秒看不见 → done=0
                                            ↓
                            第二组锥桶 → 再变一次（反向）
```

对应规则：**第一组"变道"、第二组"回线"**。

**⚠️ 这是近似方案。** 锥桶是一组**斜跨两条道**的斜线，正确做法是拟合斜线跟着走
（见第八节）。

### 3. 标线

`Marker_Scan()` 在 `imagebinary` 上逐行找特征：

- **人行横道**：一整条连续白带横跨车道（宽 ≥22px 且白点数多）
- **菱形**：同一行至少 2 条细白线，中间被黑隔开
- **停车线**：近车头（>52 行）出现单条白带

识别到横道 → 停车 5 秒 → 继续。识别到菱形 → 速度砍半。

## 六、已知问题（按严重程度）

### 🔴 1. 锥桶识别率不稳定 —— 最影响成绩

同样固件、同样赛道：`CN>=5` 的帧占比 **4% vs 31%**，一次撞一次不撞。

可能原因：光照、车的位置、锥桶角度。**这是全车最脆的地方。**

### 🔴 2. 场地太暗，摄像头已经到顶

```
imax ≈ 120（正常画面最亮只有 120/255）
曝光 2300→10000 → imax 124→122，完全没变
增益 64→124     → imax 124→123，也没变
```

- MT9V034 快门寄存器受帧长限制，1000 以上写多少都一样
- **结论：别再调曝光和增益了**

比赛场地的光跟调参的地方不一定一样，阈值要留余量。

### 🟡 3. 右偏（10 分钟能试出来）

```
duty 中位 933 = Steer_Mid 917 + Steer_Trim 16
TP 中位 59 ≈ Point_Mid 60（误差 -1，PID 基本不动作）
```

车认为自己正对中心，实际往右偏。两个可能：**摄像头朝左偏了** / 舵机中位偏了。

**试法**：page3 第 5 行 `STrim` 每次 +2，看往哪边走；或者把摄像头往**右**微转。

### 🟡 4. 菱形"逐渐减速"没做

规则要求"看到第一个减速标线后**逐渐**减速"，现在是一进状态直接砍 50%，扣 10 分。

### 🟡 5. `TP` 显示值可能超出画面

`TP=134` 出现过（画面只有 0~119）。这是**显示值**，实际送 PID 前有 `中心 ±45` 限幅
（锥桶区收紧到 `±25`），控制是正常的。别被这个数字吓到。

### ⚪ 6. 前大灯引脚未确认

暂时借用 `P20_13` / `P20_14`，接线前告诉我实际脚位。

## 七、踩过的坑（都会让人怀疑人生）

**① `zf_assert` 会静默关掉全车**

坐标越界、指针为空等断言失败后，会执行 `pit_all_close()` + `pwm_all_channel_close()` + `exti_all_close()`。
表现：**电机不转、摄像头不出图，但屏幕文字照常停在最后一帧**。

**② IPS200 坐标有上限**

`ips200_show_int` 会画 `位数+1` 个字符，每个 8px：**起始 x + 位数×8 ≤ 232**，超了触发断言。

**③ 宏必须先定义后使用**

C 语言硬要求。这个坑踩了两次（`LANE_K`、`CONE_HOLD_TICKS`），
改代码把宏加在文件后面就会报 `undeclared identifier`。

**④ 改完一定要重编**

`Debug\2024bizhang.hex` 的时间戳必须晚于所有源码。

**⑤ 屏幕调参数断电就丢**

`PARAM_TUNING=1` 表示上电不读 flash、用代码默认值。
真要用 flash 保存，把它改成 0。

**⑥ `iavg<10` 的误杀（已修，但要记住这个教训）**

`Cone_Scan` 原来抄了 `Marker_Scan` 的"画面太暗就放弃"，
但这车画面正常 `iavg` 就是 3~8（大面积黑赛道），**79% 的帧被扔掉**。

**⑦ 单边补线会算出画面外的目标点**

`L + lw*3/2` 在 L 靠右时能算出 133（画面只到 119），车会从满左直接甩到满右。
已限幅。

```
1. 把所有锥桶 blob 拟合成直线 x = a*row + b
2. 车沿这条线平行走，横向偏移半个道宽

```
