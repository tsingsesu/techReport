# 一、WiFi 图传模块

## 1.1 硬件

模块：**WIFI6B21-SPI V2.0**，插在 V3.1 的「无线模块-SPI」座（2×5，P12）。

| 座子 | 信号 | MCU |
|---|---|---|
| 1 / 3 / 5 | MISO / SCK / MOSI | `P22_1` / `P22_3` / `P22_0` |
| 2 / 4 / 10 | CS / INT / RST | `P22_2` / `P15_8` / `P23_1` |
| 7 / 8 | GND | — |
| 9 | 5V | — |

## 1.2 ⚠️ 关键改动：这块模块的 INT 引脚不能用

原版驱动每条命令都等 `INT(P15_8)` 拉高，但**这块模块的 INT 一直是低电平**（接上拉也一样），
结果初始化永远超时：屏幕 `Ver` 空白、`WiFiRet=1`。

已改为固定延时，不再依赖 INT：

```c
// libraries/zf_device/zf_device_wifi_spi.c
#define WIFI_SPI_USE_INT   (0)     // 0 = 不用 INT（当前） 1 = 库原版行为
```

| 命令 | 替代延时 |
|---|---|
| 普通命令（版本/回显/设置） | 250 ms |
| 连接 WiFi | 3 s |
| 连接 TCP | 1.5 s |

**后果：上电后到屏幕亮大约要 15 秒，期间全黑是正常的。**

## 1.3 要改的配置（换电脑/换热点必改）

`libraries/zf_device/zf_device_wifi_spi.h`

```c
#define WIFI_SPI_SPEED        (10 * 1000 * 1000)   // 已从 30MHz 降到 10MHz，长排线更稳
#define WIFI_SPI_AUTO_CONNECT (1)                  // 自动连 TCP
#define WIFI_SSID             "12"                 // ← 热点名
#define WIFI_PASS             "20070524xX"         // ← 热点密码
#define WIFI_SPI_TARGET_IP    "192.168.214.2"      // ← 电脑在热点下的 IP（必改）
#define WIFI_SPI_TARGET_PORT  "8086"               // ← 电脑端口
```

**`WIFI_SPI_TARGET_IP` 必须和逐飞助手「通信配置 → 本机地址」一模一样。**
换电脑、热点重连后 IP 会变，这里不改就连不上（助手那边「客户端」一栏会是空的）。

## 1.4 上位机操作

1. 打开逐飞助手 → 左侧「图像传输」
2. 右侧「通信配置」→ **网络** → 协议选 **TCP Server** → 本机地址选热点 IP → 端口 8086 → 连接
3. 顶部选 **「实时图像」**（不是「图片查看」）
4. 车复位后等 15 秒，「客户端」会出现车的 IP，画面开始刷新

## 1.5 图传开关（`user/cpu0_main.c`）

```c
#define CAMERA_SEND_ENABLE  (1)   // 0 = 关图传（比赛时建议关，省时间）
#define CAM_SEND_DIV        (2)   // 每 N 帧发一次；1 = 每帧都发，数字越小越流畅但越占时间
uint8 cam_send_raw = 1;           // 1 = 发灰度原图   0 = 发二值图
```

> `cam_send_raw` 可以**长按 S4 现场切换**，不用重新烧录。

## 1.6 模块诊断（page3 最下面几行）

| 显示 | 含义 |
|---|---|
| `Ver:` | 模块版本。**能显示出来 = SPI 通了** |
| `WiFiStep` | 1=版本握手 2=连 WiFi 3=连 TCP **9=全部成功** |
| `WiFiRet` | `wifi_spi_init()` 返回值，0 = 成功 |
| `Cmd` | 版本握手的回包命令字：**160=正常**、85=一个字节都没收到 |
| `INT` | P15_8 电平（本模块恒为 0，正常） |

**排查顺序**：`Ver` 空白 → 模块/接线问题；`WiFiStep` 卡在 2 → 连不上热点；卡在 3 → IP/端口不对。

# 二、新增的可调参数（page3）

原来只有几个写死的参数，现在 **5 个都能现场调，并且掉电保存**。

## 2.1 参数表

| 参数 | 作用 | 默认 | 范围 | 步长 |
|---|---|---|---|---|
| **ZYuzhi** | 二值化阈值系数（越大判为白色越少） | **109** | 20 ~ 255 | 4 |
| **Differ** | 阈值偏置 | **13** | 不限 | 1 |
| **ExpTime** | 曝光时间（µs），越大越亮 | **1010** | 60 ~ 10000 | 100 |
| **Gain** | 增益，越大越亮但噪点越多 | **44** | 16 ~ 64 | 4 |
| **STrim** | 转向微调（★新增，见 2.3） | 0 | -60 ~ 60 | 2 |

> 默认值已经按实测写进代码，队友的板子第一次烧录就是这组值。
> **换场地/换光照必须重调。**

## 2.2 按键

| 操作 | 效果 |
|---|---|
| **S2 短按** | 翻页 |
| **S5 短按** | 切下一个参数（`>` 光标移动） |
| **S3 短按** | 参数减小 |
| **S4 短按** | 参数增大 |
| **S5 长按** | **保存到 flash** |
| **S3 长按** | 恢复默认（仅 page3） |
| **S4 长按** | 图传内容 灰度 / 二值 切换 |

> 长按会先触发一次短按动作（比如 S5 会顺带切一下参数），不影响使用。

## 2.3 新增参数 STrim（转向微调）

**解决机械偏转**：舵机中位不准、左右轮摩擦不同、摄像头装偏，都会让车在直道上**恒定跑偏**。

```c
// code/control.c
int16 Steer_Trim = 0;

SD5_Duty = PID输出 + Steer_Trim;          // 有边线时
SD5_Duty = SteerMiddle + Steer_Trim;      // 没边线时
```

**方向：duty 越大越往左。**

| 现象 | 操作 |
|---|---|
| 直道往右偏 | STrim 往**正**调（S4） |
| 直道往左偏 | STrim 往**负**调（S3） |

一般 ±10～30 就够。

## 2.4 掉电保存

- 5 个参数存到 **flash 第 11 页**
- 上电 `Parameter_Read()`：**先查有效标记，再逐项校验范围**，不合法就退回代码默认值
  （之前没校验时读出垃圾值导致 `zyuzhi=0`，二值图全黑）

# 四、必须知道的三个坑

**① 屏幕坐标有上限**：`ips200_show_int` 会画 `位数+1` 个字符，字符宽 8 像素：
`起始 x + 位数×8 ≤ 232`，超了触发断言。

**② 断言会静默关掉一切**：`zf_assert` 失败会执行 `pit_all_close()` + `pwm_all_channel_close()` + `exti_all_close()`，
表现为**电机不转、摄像头不出图，但屏幕文字照常刷新**。

**③ 烧录后按复位**：AURIX Flasher 烧完 CPU 可能停在 halt，程序不跑。
另外**别用下载器供电**，电压不够会让屏幕/WiFi 出怪问题。

# 五、2026-10-24：ToF 发车检测提速

## 现象

`To=8192` 占日志 91%，`hits` 最大只有 20，**车从来不发车**。

## 根因（两个）

**① 8192 不是故障，是"这一轮还没测完"**

`zf_device_dl1b.c` 里：

```c
dl1b_transfer_8bit_array(data_buffer, 2, &data_buffer[2], 1);
if(data_buffer[2])      // ← 只有新一轮测完中断标志才置位
{   ...读距离... }
else
{   dl1b_distance_mm = 8192; }   // ← 没测完也写 8192
```

DL1B 约 20~50ms 才出一帧，`cpu1_main` 一直在高速轮询，
所以 90% 的读取都落在"还没测完"上，写出 8192。**正常现象**。

**② 旧判定按"时间窗"计数，永远凑不够**

```c
if(++tf_win >= 60)                    // 6×5ms 的定时窗口
    if(tf_valid_n >= 8 ...)           // 要求窗内 8 个有效样本
```

窗口里只有 3~6 个有效样本，`>= 8` 永远达不到 → 死锁。

**③ 附带一个隐患**：`dl1b_distance_mm` 有效值只存在几百微秒就被下一轮 8192 冲掉，
10ms 的中断经常**根本采不到它**。

## 改法

| 文件 | 改动 |
|---|---|
| `user/cpu1_main.c` | 读到新距离时把值搬到 `tof_sample_mm` 并置 `tof_new_sample=1`，再清 `dl1b_finsh_flag` |
| `code/Img_analyse.c` | 新增 `volatile uint16 tof_sample_mm` / `volatile uint8 tof_new_sample` |
| `user/isr.c` | 判定改成**只消费新样本**，按样本数而不是时间计数 |

判定参数（`user/isr.c` 顶部）：

```c
#define TF_BASE_N   (6)    // 6 个样本建立地面基线
#define TF_WIN_N    (10)   // 滚动窗口
#define TF_HIT_N    (7)    // 10 个里 7 个被挡 → 发车
#define TF_RUN_N    (5)    // 连续 5 个被挡 → 立刻发车（快通道）
```

命中条件：`d + 15 < 基线`（比地面基线近 15mm 才算遮挡）。

**响应时间**：基线 6 个样本 ≈ 0.3s，之后连续 5 个样本 ≈ 0.25s，
**挥手到发车总共约 0.5s**（原来是不发车）。

## 怎么验证

日志里看 `SB=ready/base/hold`：

- `SB=0/0/0` → 还没采够 6 个样本（等 0.5s 就好）
- `SB=1/64/0` → 基线成型（地面 64mm），当前没被挡
- `SB=1/64/5` → **已经触发发车**
- `SB=1/64/7` → 走常规通道触发

## 要再快/再稳改哪里

| 想要 | 改 |
|---|---|
| 更容易触发 | `TF_HIT_N` 7→6，或 `TF_RUN_N` 5→4 |
| 更不容易误触发（地面颠簸） | `d + 15` 的 15 调大，如 20~25 |
| 基线更快 | `TF_BASE_N` 6→4（但基线噪声变大） |

# 六、2026-10-24：车道宽度归一化（解决"左道右道来回穿梭"）

## 先搞清楚算法到底在看什么

`Img_analyse.c`：

```c
Mid_Line[60] = 60;                                          // 从画面底部正中心开始
Traversal_Mid_Line(i, data, Mid_Line[i+1], 1, COL-3, ...);  // 向左右各找"第一处白色跳变"
```

**它不是在看"两条道"，而是只跟一条道** —— 离画面中心最近的那两条白线包出来的那一块。
虚线也算边界，不区分实线/虚线。

## 真正的病根：同一帧的宽度会跳

从日志 `log_20261024_163738.txt`（729 帧）统计：

```
L 中位 37    R 中位 95    W 中位 43
R = 117（扫描上限 = 没找到）占 173 次 = 24%
W 双峰：30~49 有 40 帧    80~119 有 27 帧
```

原因：

| 情况 | 扫描结果 | 宽度 |
|---|---|---|
| 虚线这一行**有**白色 | 扫到「左实线 + 虚线」 | **≈43px**（一条道） |
| 虚线这一行是**断口** | 整条虚线被跳过 → 扫到整条路 | **≈90~116px**（两条道） |

原来的公式 `Pt = L + W × lane_k%` 用的是检测到的 W：

- W=43 → Pt = L + 32（已经贴到右边缘外）
- W=116 → Pt = L + 87（这才是右道中心）

**同一个 lane_k，在两种宽度下算的根本不是同一个位置** → 车在两道之间来回穿梭。
不是舵机也不是 PID 的问题。

另外 `w_ema` 会把 116 也学进去，导致单边补线时推出去 44px，越推越偏。

## 改法（`code/control.c`）

```c
#define STEER_ONE_LANE_MAX   (70)    // 小于它 = 一条道；大于它 = 扫到了整条路
#define STEER_LANE_W_DEF     (43)    // 单道宽兜底值
```

| 情况 | 目标点 |
|---|---|
| w ≤ 70（一条道） | `L + w/2` —— 车当前所在那条道的中心 |
| w > 70（整条路），lane_k ≤ 50 | `L + w/4` —— 左道中心 |
| w > 70（整条路），lane_k > 50 | `L + 3w/4` —— 右道中心 |
| 只有左边线 | `L + 单道宽/2` |
| 只有右边线 | `R - 单道宽/2` |
| 两边都没线 | 回中位 |

**`w_ema` 改成 `lane_w_ema`，只学 ≤70 的样本**，不再被整条路污染。

## lane_k 的含义变了

```
<= 50  = 左道中心
>  50  = 右道中心        （默认 75 = 右道）
```

它现在**只在"扫到整条路"那一帧起作用**；扫到一条道时永远是"待在本道中心"，
不会在两个道之间跳。屏幕 page3 的 LaneK 还是 ±2 调，跨过 50 就换道。

## 能保证和不能保证的

✅ 不会再因为宽度跳变而在两道之间穿
✅ 不会因为 `R=117` 那种兜底值把目标点推到画面外

⚠️ 它只能保证「待在车现在所在的那条道里」。
**发车时车必须停在右道上**，否则它会稳稳地跑左道。

## 验证

日志里看 `L / R / W / TP`：

- `W≈43`、`TP ≈ L+21` → 单道模式，正常
- `W≈90~116`、`TP ≈ L+67` → 整条路模式，取的右道中心
- `TP` 不再在两种值之间来回跳，就是修好了

# 七、2026-10-24：ToF 发车判据重写（朝前安装）

## 现场数据揭穿的两个问题

**① `8192` 占 67%，最长连续 13.2 秒没有有效读数**

`dl1b_get_distance()` 里，IIC 读失败和"这一轮没测完"**都会写 8192**，两者无法区分。
而驱动默认的软件 IIC 是 `DL1B_SOFT_IIC_DELAY (10)` ≈ **1020KHz**，
头文件自己写着「DL1B 最高支持 400KHz」——**超规格 2.5 倍**。

→ 改成 `( 50 )` ≈ 448KHz（`libraries/zf_device/zf_device_dl1b.h`）。

**② 基线是在「手挡着」的时候建立的，所以永远发不了车**

```
SB(base)：0,0,0,0, 32,32,32, 26,26,37,...
```

前 34 帧 base=0（前方空旷，读到 8192 被过滤）；手一伸进去，基线就用**手的距离 32mm** 建起来了。
之后手拿开 → 8192；手再伸 → 30mm ≈ 基线 → 判不出遮挡。

**「遮挡」变成了基线本身**，这就是 `hold` 全程为 0 的原因。

## 新判据（`user/isr.c`）

朝前看的 ToF 逻辑本来更简单：前方空旷 = 测不到，有东西进入光束 = 出现近距读数。

```c
#define TF_NEAR_MM   (500)   // 50cm 以内才算"有东西挡前面"
#define TF_WIN_N     (12)    // 最近 12 个有效样本
#define TF_HIT_N     (8)     // 12 个里 8 个近距 → 发车
#define TF_ARM_TICKS (200)   // 5ms × 200 = 1 秒"前方空旷"才布防
```

1. 先看够 **1 秒前方空旷**（一个有效样本都没有）→ 布防
2. 布防后，最近 12 个样本里 **8 个 <50cm** → 发车
3. 车停在墙边时一开始就读到近距，**布不了防，不会抢跑**

基线（`tf_ema`）彻底不用了。

## 屏幕上看得到（page3 最后一行）

```
To <读数>   A <是否布防>   H <命中计数>
```

- `To=8192` 前方空旷；`To=30` 有东西在 3cm 前
- `A=0` 还没布防；`A=1` 可以挥手
- `H` 从 0 涨到 8 就发车

挥手测的时候不用真发车：`START_MODE=2` 下 `start_trigger` 被忽略，
只看 `H` 有没有涨到 8 就能确认判定对不对。

## 注意

- **`A` 一直是 0** → 前方一直有东西（一直读到 <50cm），永远布不了防。告诉我改条件。
- `START_MODE` 现在是 **2**（上电 20 秒自动发车）。ToF 验证完改回 **1**。

# 八、2026-10-24：宽度模式加迟滞

## 为什么

起步后实测（169 帧有线数据）：

```
W 分档： <60 单道 21%   60~70 单道 28%   70~85 灰区 18%   >85 整条路 33%
以 70 为界翻转 26 次 / 169 帧
相邻 TP 跳 >15px 有 29 次，最大一次 92px
```

W 是**连续分布**（58~116），不是干净的两档。70 这条分界正好切在中间，
抖动一下就在「本道中心」和「整条路右道中心」两种算法之间切换。

## 改法（`code/control.c`）

```c
#define STEER_WIDE_ON    (85)   // 超过它才算整条路
#define STEER_WIDE_OFF   (60)   // 低于它才算一条道
```

```c
static uint8 wide_mode = 0;
if(w > STEER_WIDE_ON)       wide_mode = 1;
else if(w < STEER_WIDE_OFF) wide_mode = 0;   // 60~85 保持上次判断
```

## 顺带说明

- `duty` 贴上限（>=980）只占 3%，贴下限占 0% —— 舵机没有一直堵在极限
- 相邻 TP 变化中位只有 2px —— 大部分时候本来就是平顺的，只有模式切换那一下会跳

# 九、2026-10-24：横道前右偏（不可信帧保持）

## 现象

人行横道前车头往右偏。日志里抓到：

```
T=130  P=36  LC=27  L=1   R=83  W=82  duty=934  TP=57
T=133  P=2   LC=51  L=1   R=83  W=82  duty=934  TP=57   GB=0x0504
T=137  P=2         L=19  R=109 W=90  duty=863  TP=86   ← 右限位
```

## 原因

横道的白色横条把整幅画面填满 → 中线拟合塌到 `P=2`（图像最左边），
这是明确的「这一帧不可信」信号，`steer_guard_bits` **已经检测到了**
（`GB=0x0004` 就是 `Point<=6`），**但这个变量算出来没人用**，舵机照样拿垃圾数据打方向：

```
L 1→19，W 82→90（越过 85）→ 切成"整条路"模式 → TP 57→86 → duty 934→863
```

还有更离谱的一帧：`L=100 R=117 W=17`，单边补线算出 `TP=127`（跑出画面）。

## 改法（`code/control.c`）

**① 真正用起 `steer_guard_bits`**

```c
if(pt < 0) bad = 1;
if(steer_guard_bits & (0x0004 | 0x0008 | 0x1000)) bad = 1;
```

- `0x0004` = `Point <= 6`（中线拟合塌到最左）
- `0x0008` = `Point >= W-6`（塌到最右）
- `0x1000` = `Result_Far_Row < 40`（可信行太少）

命中就**沿用上一次的可信目标点**；连续 2 秒都不可信才回中位（防止真丢线时一直保持错误方向）。

**② 单边补线加位置合理性**

```
左边线必须在画面左 3/4 内（L < 90）
右边线必须在右 3/4 内（R > 30）
```

否则视为无效（`L=100` 却当左边界用，补半个道宽就飞出去了）。

## 验证

重跑一次看横道前那几帧：

- 修好：`TP` 稳在 57 附近，`duty` 稳在 934 附近
- 没修好：`TP` 还会跳到 86、`duty` 掉到 863

# 十、2026-10-24 夜间：锥形标识别 + 绕行（5 版迭代）

> 这一段记录全过程，因为踩了很多坑。**结论在最后。**

## 目标

规则：两组锥桶（每组 5~7 个，与中线约 30° 夹角）→ 按锥桶线路行驶 → 菱形减速 → 横道前停车 5 秒。

## 关键认知：红色锥桶在灰度图里是「白」的

```
红色 (255,0,0) → 灰度 ≈76
黑赛道         → 约 20~40
白线           → 200 以上
二值阈值 T0    → 约 48
```

76 > 48，**红色整体变白**，跟车道线一样白。所以不能靠颜色，只能靠**横向宽度**：

```
车道线 2cm → 2~3px（细）
锥桶白箍   → 5~10px（粗）   ← 实测直方图 b 档每帧 14~23 个
```

## 第 1~3 版：各种识别不出来

| 版本 | 问题 | 修法 |
|---|---|---|
| v1 | blob 计数逻辑错："上一行没宽白段才算新锥桶"，但每行都有几十个 | 改二维 blob 跟踪 |
| v2 | `cone_x` 一直卡在 108（右边界才 100） | 只在车道内部扫 |
| v3 | `CN` 永远 1~2 | 见下面两条 |

**v3 的两个真凶：**

**① `iavg<10` 误杀（最致命）**

`Cone_Scan` 开头抄了 `Marker_Scan` 的"画面太暗就放弃"：

```c
if(diedai_img_avg > 190 || diedai_img_avg < 10) { cone_ok = 0; return; }
```

但**这车画面正常 `iavg` 就是 3~8**（大面积黑赛道），结果 **79% 的帧被扔掉**。
只有画面恰好亮一点的帧才能扫 → 识别率 13%。

**② `CONE_MIN_ROWS` 要求 2 行**

锥桶白箍只有 1cm 高，二值化后**就是 1 行**。要求 2 行等于全扔。

改成 `CONE_MIN_ROWS = 1` 后，`CN` 从 1~2 跳到 6~11。

> 验证：日志里 `CWD=21/14/2/0/0` —— 5~10px 这档有 14 个白段，
> 说明锥桶确实被检测到了，只是被"至少 2 行"的门槛全过滤了。

## 第 4~5 版：认出来了，但车乱转

| 现象 | 根因 | 修法 |
|---|---|---|
| 满舵左打 2 秒多，冲出赛道 | 锁存"每次看到锥桶都续期"，锥桶一组 2~4 米，一直看得见就一直转 | 改成固定时长（1.0 秒），不续期 |
| 转一下又回正，来回摆 | 10 帧（50ms）看不到锥桶就退出 | 改成锁存 |
| 连续左满舵 8 次，越转越左 | 冷却 1.5 秒 + 还能看见锥桶 → 冷却一结束又变道 | 改成"锥桶离开视野 1 秒才算这组过完"（`done`/`clear_cnt`） |
| 一会儿左满舵一会儿右满舵 | `cone_x` 取"最近那个 blob"，实测相邻帧 61→102→79→37 | 改取平均（见下） |

## 最重要的教训：变道只能靠「时间」，不能靠「误差」

```c
pt = Point_Mid ± CONE_LANE_HALF;   // 绝对目标点
```

但**检测到的车道是跟着车走的**——车往左挪，车道在画面里也往左挪，`Point` 又回到 60，
误差重新出现，于是**一直往左打**。

所以变道的量不能靠 PID 收敛控制，**只能靠固定时长**（1.0 秒）。

## 最终版本的行为

```
看到锥桶(CN>=2) → 按近端锥桶位置定方向 → 满舵打 1.0 秒 → done=1
                                              ↓
                              之后看得见锥桶也不再变道
                                              ↓
                              锥桶连续 1 秒看不见 → done=0
                                              ↓
                              第二组锥桶 → 再变一次（反向）
```

## 关键参数

| 宏 | 位置 | 当前 | 说明 |
|---|---|---|---|
| `CONE_W_MIN/MAX` | `Img_analyse.c` | 5 / 40 | 白段宽度，排除 2~3px 的车道线 |
| `CONE_MIN_ROWS` | `Img_analyse.c` | **1** | **必须是 1**，白箍只有 1 行高 |
| `CONE_NEAR_ROW` | `Img_analyse.c` | 36 | 多大行号算"近端"，绕行方向用它 |
| `CONE_HOLD_TICKS` | `control.c` | 200 | 变道动作时长 1.0 秒 |
| `CONE_LANE_HALF` | `control.c` | 22 | 变道目标点 = 中心 ±22px |
| `CONE_CLEAR_TICKS` | `control.c` | 200 | 锥桶离开 1 秒算这组过完 |
| `CONE_ACT_ENABLE` | `Lu_UI.h` | 1 | 总开关 |

## 还没解决 / 已知风险

1. **识别率不稳定**：同样固件同样赛道，`CN>=5` 的帧占比 **4% ↔ 31%**，一次撞一次不撞。
   这是目前最大的不确定性。

2. **锥桶是斜跨两条道的**，车本该沿斜线走。当前"打 1 秒方向"是**近似**。
   如果还过不去，正确做法是：把所有 blob 拟合成直线 `x = a*row + b`，
   车沿这条线平行走。检测部分不用改，`cone_px[]/cone_py[]` 已经在存了。

3. **场地太暗，摄像头已到顶**：
   曝光 2300→10000 没用（寄存器被帧长截断），增益 64→124 也没用。`imax` 恒定 ≈120。

4. 单边补线可能算出画面外的目标点（实测 `TP=134`），已限幅在 `中心 ±45`，
   锥桶区收紧到 `±25`。
